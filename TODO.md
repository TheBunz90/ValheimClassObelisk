## Done

- [x] **Arrow Slinger (and other bow/spear-only perks) proccing off unrelated hits.** Reported: Archer's Arrow Slinger buff was proccing while running through the Black Forest as Greydwarfs threw rocks, despite no bow being fired. Root cause: `ArcherPerkManager`'s (and identically, `LancerPerkManager`'s) `Projectile.OnHit` patch used a `FindProjectileOwner` helper that fell back to "whichever player is within 100m" whenever a projectile had no resolvable ZDO owner - true for any monster-thrown projectile (Greydwarf rocks, etc.) that happens to land on some other nearby creature, misattributing it to whichever player was standing nearby and proccing their bow/spear perks regardless of what actually hit what. This predates this session's changes (confirmed via `git log` - untouched by any of our recent commits). Fixed by reading the projectile's own `m_owner`/`m_skill` fields directly (set once in `Projectile.Setup` and authoritative - `m_owner` needed Harmony's `___m_owner` field-injection since it's private on the real class) instead of guessing, and explicitly gating on the shot/throw actually being the right skill type (Bows/Crossbows for Archer, Spears for Lancer). Deleted both now-dead `FindProjectileOwner` helpers. **Note:** a third, structurally-identical copy of this same pattern (`ClassCombatManager.ResolveProjectileOwner`) exists but is dead code - its only caller is inside a commented-out block - so it was left alone rather than touched unnecessarily; flag if you'd like it cleaned up too. See CHANGELOG.md (Unreleased).
- [x] **Fix level up logic.** `CheckForLevelUp` only ever compared XP against the very next level's threshold and advanced by exactly 1, so a kill with enough XP for multiple levels would get stuck one level behind until the next kill "caught it up". Now uses the existing `XPCurveHelper.GetLevelFromXP(totalXP)` (already used elsewhere for progress display) to set the level directly to whatever the total XP actually corresponds to. Also fixed `RPC_ReceiveClassXPAward`'s "New Perk Unlocked!" message, which only fired when the final level was itself a multiple of 10 - it now announces every perk tier (10/20/30/40/50) crossed during the jump, so a multi-level kill can no longer skip a perk-unlock notification. See CHANGELOG.md (Unreleased).
- [x] **Add Dual Class Notification.** There was previously no dedicated signal for this milestone at all - level 50 fired the same generic "Level Up!"/"Perk Unlocked!" toasts as every other level. Added a one-time "★ Dual Class Unlocked! ★" center-screen message in `RPC_ReceiveClassXPAward`, firing exactly when `CanSelectSecondClass()` flips false→true (the first class of the character to hit 50 - later classes reaching 50 won't repeat it). Also moved the Compendium's existing "A second class slot is available" note from the bottom of the "Active Classes" entry to the top, and made it bold/gold instead of gray, so it's the first thing seen rather than something to scroll past. Left the Obelisk panel's existing open-time hint text and perk descriptions unchanged per discussion (no advance-notice spoilers, no new persistent UI element). See CHANGELOG.md (1.0.4).
- [x] **Class XP persists across character deletion / reuse of a character name.** Root cause (confirmed via decompiling Valheim's own code): the main-menu character-preview model (`FejdStartup.SetupCharacterPreview`) is instantiated with `ZNetView` deliberately disabled, so it never gets a real ZDO and `Player.GetPlayerID()` always returns 0 for it - yet both browsing the character list and finishing "New Character" route through the same `Player.Save`/`Player.Load` calls our mod patches. That let one real character's class data get cached in memory under the shared key `0` while previewing it in the menu, then get baked straight into the next new character's first save - nothing to do with names or deletion, the leak happens in memory at menu time. Fixed by skipping both `Player_Save_Patch` and `Player_Load_Patch` whenever `GetPlayerID() == 0`. **Note:** this only stops the leak going forward - any character save that already inherited wrong XP before this fix stays wrong; no retroactive repair was done. See CHANGELOG.md (1.0.4).
- [x] **Second class slot (unlocked at level 50) can't actually be selected.** Root cause: the only wired-up selection method always replaced the active class list with one entry, and the correctly-eligibility-aware add/remove methods existed but were never called; the Obelisk UI was also a single-select radio pattern with no way to pick a second class at all. Fixed by adding `PlayerClassManager.ActivateClass`/`DeactivateClass` (add-if-room, swap if only 1 slot unlocked, block if both of 2 slots are full) and reworking the Obelisk panel: class buttons preview descriptions (green-highlighted when active), and a dynamic Activate/Deactivate button + italic "class limit reached" hint at the bottom drives the actual state change - all in-panel, since MessageHud toasts render underneath the panel and are invisible while it's open. See CHANGELOG.md (1.0.4).
