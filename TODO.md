- [x] **Perk rework, Phase 2: Assassin, Brawler, Bulwark rewrites.** Full rewrite of all three to the new 5-tier shape from `class-perks-rework.json`. Notable along the way: (1) fixed Assassin's Level 10 double-damage-bonus (same pattern as the still-open Crusher/Lancer instances) by consolidating Cutthroat's flat bonus into `ClassCombatManager` only; (2) fixed a real bug in Assassin's Twist the Knife - it was applying its damage bonus to every hit, not just hits against poisoned targets as the perk describes; (3) fixed Brawler's Tough/Rage perks checking the *attacker's* Brawler level for damage-taken effects instead of the *target's* (backwards); (4) moved Brawler's combo counter and Rage state, and Bulwark's new Perfect Guard empower window, from module-level statics (shared across every player) to per-player dictionaries; (5) Bulwark's new "Perfect Guard" (parry-triggered) reuses Sword Master's existing timed-block detection (`m_blockTimer` reflection) rather than reinventing it; (6) Axemaster/Bulwark's new movement-penalty-removal perks (Woodsman's Carry / Shield Bearer) offset only their own item's contribution via `Player.GetEquipmentMovementModifier`, avoiding Crusher's existing approach of mutating shared item data (`item.m_shared.m_movementModifier = 0f`), which looks like it leaks the change to every player's copy of that item type; (7) Rage's trigger was simplified per feedback to fire on any damage taken, not just unblocked damage - the original "unblocked" check relied on `!player.IsBlocking()` at a patch point that runs before vanilla's own block resolution, an imprecise signal not worth the complexity; (8) added a new Silent Hands (L20) effect per follow-up request, then simplified per further feedback (the original "+25% crouch speed" was hard to notice while testing) to "move at normal walking speed while crouched" - a much more perceptible effect, and reads the player's own live `m_walkSpeed` rather than a fixed multiplier since walk speed (unlike jog/run) isn't itself scaled by equipment penalties in vanilla. `Character.m_crouchSpeed` turned out to be a plain per-instance field (not shared item data), read fresh every frame by the game's own movement code, so it's set directly rather than needing a patched getter. Refreshing on spawn + on-hit wasn't actually taking effect in testing, though; moved to a `Player.SetCrouch` postfix per follow-up feedback instead - `SetCrouch` is just `m_crouchToggled = crouch`, the exact moment the player toggles crouch on/off, so tying the refresh directly to that action is both more reliable and more correct than the reactive spawn/hit approach (still keeps the spawn hook as a harmless extra safety net; dropped the on-hit one entirely, since it no longer serves a purpose once the real trigger is wired up). Still not confirmed working as of the `SetCrouch` fix, so added temporary `DevLog` diagnostics (a Debug-only per-toggle log plus a once-a-second snapshot) and asked for a `LogOutput.log` capture - which immediately settled it: `m_crouchSpeed` WAS being set correctly and held its value (no bug in our logic at all), but the reference point was wrong for what was actually wanted. The perk was matching `m_walkSpeed` (the toggled walk-mode speed, already close to vanilla's own crouch speed - and in this install, reduced by Valheim Plus's movement-speed settings to ~1.6, slower than vanilla's default crouch speed of 2), not `m_speed` (the normal jog/run baseline, ~4 in the same log) - which is what was actually meant by "normal movement speed." Switched the perk (and its cached-before-`SetCrouch` value) to use `m_speed` instead, removed the now-served-their-purpose diagnostic logs, and updated the perk description to say "normal movement speed" rather than "normal walking speed" to avoid the same ambiguity going forward. (9) Rage's attack-speed buff was reported as making attacks feel *slower*, not faster. Root cause: vanilla's own unarmed combo animation already varies `Animator.speed` across a swing's phases (observed fluctuating between 1.0 and 2.0 via diagnostic logging), and `AnimationSpeedManager.ApplyIfNeeded` was overwriting that with a flat absolute value instead of scaling it - so any phase vanilla had already sped up past our target got knocked back down. Switched to multiplying relative to vanilla's current value instead of replacing it. That introduced a second bug caught by the same log-then-fix loop: `Animator.speed` is a persistent field vanilla only rewrites at certain phase transitions (not every tick), so on the ticks in between, reading it back as "the base" was actually reading our own prior output and re-multiplying it, compounding exponentially (confirmed via log - a clean geometric ×1.10 chain up to 5.19). Fixed by tracking the value we last wrote per-character and only rescaling when `Animator.speed` no longer matches it (meaning vanilla set a fresh base since); otherwise left alone. Also tuned Rage's numbers twice per feedback after playtesting the fix: damage bonus down from +20% to +10% (felt too strong once attack speed worked correctly), attack speed tried at +10% then settled back at +20% (felt too weak at +10% once the compounding bug was gone). Not yet in CHANGELOG.md - still holding for one coherent entry once more of the rework lands.

- [x] **Assassin poison was fighting vanilla's own poison system, roughly double-applying damage.** Venom Coating manually ticked poison damage once per second via its own `Game.Update` loop, calling `target.Damage()` each time. Since that re-enters vanilla's own `Character.RPC_Damage` → `AddPoisonDamage` → `SE_Poison.AddDamage()` (confirmed via decompiling Valheim's `Character`/`SE_Poison`/`StatusEffect` classes), and `SE_Poison.AddDamage` is a "replace pool + reset timer" call, our manual ticks kept restarting vanilla's own concurrently-running 1-second tick - so the target was taking damage from both our tick and vanilla's own tick at roughly the same cadence. Fixed by computing the stack-scaled total once per knife hit and handing it to vanilla's `SE_Poison` a single time, letting vanilla own all the actual tick timing/damage/visuals/sound from there (duration is now damage-derived, `~2 + √(total×2)` seconds, matching every other poison source in the game, rather than a fixed 10s). Verified separately that vanilla's own tick cadence (`SE_Poison.m_timer`) is unaffected by repeated `AddDamage()` calls, so fast auto-attacking with a knife can't starve poison of ticks. Also fixed two bugs found while rewriting this code: the Envenomous movement slow was compounding incorrectly across stacks (it recaptured "original speed" from the already-slowed value on every stack instead of a stable baseline), and it was applying at any Assassin level instead of being gated to the Level 30 "Envenomous" perk as intended. See CHANGELOG.md (1.0.5).
- [x] **Arrow Slinger (and other bow/spear-only perks) proccing off unrelated hits.** Reported: Archer's Arrow Slinger buff was proccing while running through the Black Forest as Greydwarfs threw rocks, despite no bow being fired. Root cause: `ArcherPerkManager`'s (and identically, `LancerPerkManager`'s) `Projectile.OnHit` patch used a `FindProjectileOwner` helper that fell back to "whichever player is within 100m" whenever a projectile had no resolvable ZDO owner - true for any monster-thrown projectile (Greydwarf rocks, etc.) that happens to land on some other nearby creature, misattributing it to whichever player was standing nearby and proccing their bow/spear perks regardless of what actually hit what. This predates this session's changes (confirmed via `git log` - untouched by any of our recent commits). Fixed by reading the projectile's own `m_owner`/`m_skill` fields directly (set once in `Projectile.Setup` and authoritative - `m_owner` needed Harmony's `___m_owner` field-injection since it's private on the real class) instead of guessing, and explicitly gating on the shot/throw actually being the right skill type (Bows/Crossbows for Archer, Spears for Lancer). Deleted both now-dead `FindProjectileOwner` helpers. **Note:** a third, structurally-identical copy of this same pattern (`ClassCombatManager.ResolveProjectileOwner`) exists but is dead code - its only caller is inside a commented-out block - so it was left alone rather than touched unnecessarily; flag if you'd like it cleaned up too. See CHANGELOG.md (1.0.5).

- [x] **Class XP persists across character deletion / reuse of a character name.** Root cause (confirmed via decompiling Valheim's own code): the main-menu character-preview model (`FejdStartup.SetupCharacterPreview`) is instantiated with `ZNetView` deliberately disabled, so it never gets a real ZDO and `Player.GetPlayerID()` always returns 0 for it - yet both browsing the character list and finishing "New Character" route through the same `Player.Save`/`Player.Load` calls our mod patches. That let one real character's class data get cached in memory under the shared key `0` while previewing it in the menu, then get baked straight into the next new character's first save - nothing to do with names or deletion, the leak happens in memory at menu time. Fixed by skipping both `Player_Save_Patch` and `Player_Load_Patch` whenever `GetPlayerID() == 0`. **Note:** this only stops the leak going forward - any character save that already inherited wrong XP before this fix stays wrong; no retroactive repair was done. See CHANGELOG.md (1.0.4).
